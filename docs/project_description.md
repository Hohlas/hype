# Алгоритм бота: спот-сетка с отложенными ордерами

Параметры (имена — ключи `settings.py`):

- `SPOT_TOKEN` — торгуемый спот-актив (сейчас BTC).
- `STEP` — шаг сетки в долларах: расстояние усреднения и цель каждого тейка.
- `POSITION_SIZE_PERCENT` — размер одного входа в процентах от доступного USDC.
- `AGGR` — доля шага для входа вдогонку растущей цене (0.1–1.0).
- `BUYLIMIT_LEVEL_COOLDOWN_SEC` — пауза перед повторным входом на тот же уровень
  (константа, 600 с; в конфигурацию не вынесена).

## 1. Цикл

Итеративный цикл с паузой между итерациями. Каждая итерация получает: текущую
спот-цену, открытые ордера, балансы. Открытые ордера делятся на лимитные покупки
(BuyLimit, всегда не более одного активного) и лимитные продажи (тейки). По
висящим тейкам определяются `min_TP` (самая низкая цена продажи) и `max_TP`
(самая высокая).

Размер каждого входа — `POSITION_SIZE_PERCENT` от доступного USDC, но не ниже
биржевых минимумов. По мере траты USDC следующие входы уменьшаются; глубина
сетки ограничена только доступным USDC.

Дисциплина цикла — в разделе «Дежурство (GitHub Actions)» ниже (в дежурстве цикл
ограничен вотчем; в VPS-режиме бесконечный).

## 2. Три ветки входов

1. **Первый вход** — если висящих тейков нет вообще: покупка по рынку на размер
   входа по текущей цене. Повтор не допускается, пока для свежей покупки не
   подтверждён тейк (защита от дублей входов по одной цене).
2. **Усреднение вниз** — лимитный ордер на покупку по цене `min_TP − 2×STEP`.
   Ставится только при отсутствии активного BuyLimit и висит до исполнения.
   Устаревший ордер отменяется: если его цена оказалась ниже
   `min_TP − 2.5×STEP`, он снимается и выставляется заново по актуальной формуле.
3. **Вход вдогонку вверх** — покупка по рынку, если текущая цена выше
   `max_TP − AGGR×STEP`.

## 3. Правило повторного входа

Один исполненный вход — один тейк. Повторная покупка на том же ценовом уровне
запрещена, пока не подтверждено исполнение тейка предыдущего входа с этого
уровня. Нарушение запрета дополнительно сдерживается паузой
`BUYLIMIT_LEVEL_COOLDOWN_SEC` после исполнения тейка.

При старте бот находит покупки без тейков и ставит на них тейки; если для тейка
не хватает свободного остатка (меньше биржевого минимума), постановка
откладывается до появления баланса.

## 4. Тейки и учёт прибыли

На каждую новую покупку ставится лимитный ордер на продажу всего купленного
объёма по цене `вход + STEP`. Исполнение тейка подтверждается историей сделок.
Прибыль сделки = фактическая выручка продажи минус фактические затраты покупки
(цены и комиссии исполнения, при частичном исполнении — пропорционально проданной
доле). Если покупка в истории не найдена, прибыль оценивается как `STEP` минус
комиссии обеих сторон.

Каждая операция записывается в таблицу статистики (`hype_stat.csv`, стандартная
библиотека `csv`) и отправляется в Telegram.

## 5. Границы

Стоп-лоссов нет, тейки не отменяются и не двигаются: купленный актив удерживается
в споте неограниченно долго. В монотонном росте каждый вход продаётся целиком на
`вход + STEP`, поэтому позиция в тренде мала и сетка отстаёт от buy-and-hold.

## 6. Дежурство (GitHub Actions)

Прод живёт в GitHub Actions: короткие запуски по расписанию образуют эстафету.
В каждый момент один запуск — **ведущий** (торгует), остальные — **ожидающие**
(запущены рядом, торговли не ведут, следят за флагом и готовы подхватить).
Конвейер описан в `.github/workflows/bot.yml`; логика протокола — `modules/duty.py`.

### 6.1. Общее состояние — ветка `state`

Единственное место, доступное любому запуску, — ветка `state` (запись через
GitHub Contents API). Файлы: `state.json` (метки, счётчики и невосстанавливаемая
с биржи память), `leader.json` (кто ведущий и жив ли), `standby.json` (последний
ожидающий), `work.json` (маркер «работа движется»).

### 6.2. Инварианты протокола

- **Заявка.** Новый запуск заявляет `ready: false`; флаг `ready: true` ставится
  только после успешной связи с биржей и первого разбора. Запуск, не достучавшийся
  до биржи, ведущим не выглядит.
- **Уступка.** Ведущий уступает только живому, готовому и строго более новому
  ведущему; при равном времени старта побеждает больший `run_id`.
- **Подхват.** Флаг отсутствует, стук сердца старше `LEADER_STALE_SEC=300` или
  ведущий `retiring` → подхват после `PROMOTE_CONFIRM_READS=2` подтверждающих
  чтений. Клин (сердце свежее, но `work.json` того же `run_id` старше
  `WORK_STALE_SEC=900`) — то же правило.
- **Наследование дедлайна.** Подхвативший ожидающий ведёт ОСТАТОК своего вотча,
  а не полный заново. Иначе новый дедлайн переживает лимит задания и запуск
  убивает платформа.
- **Слияние состояния.** Только объединение: метки — свежайшая дата на ключ,
  счётчики и `last_run_utc` — максимум. Запись: прочитать → слить → записать →
  проверить.
- **Стук сердца** — отдельной фоновой задачей, не в теле торгового цикла: стук
  по итерациям замерзает на длинной задаче, и живой ведущий выглядит мёртвым.

### 6.3. Бюджет времени

Формула: `вотч + хвост + установка ≤ timeout-minutes`. В `bot.yml`:
`330 (вотч) + 15 (хвост) + 1 (установка) = 346 ≤ 355` (потолок платформы 360).
Дедлайн проверяется между итерациями; начатая итерация дорабатывает целиком,
поэтому хвост обязателен. Подпись убийства — `conclusion: cancelled` с
длительностью ≈ `timeout-minutes`.

### 6.4. Каденс

cron `7,19,33,46,58 * * * *` (UTC): мимо пика начала часа (`:00–:05`, задержки и
потери тиков) и мимо круглых минут. `concurrency` в workflow нет намеренно:
перекрытие запусков — часть дизайна, арбитраж делает протокол, а не очередь.
Факт: планировщик GitHub роняет большинство тиков, рождения идут раз в часы —
тик расписания и факт запуска не одно и то же.

### 6.5. Режим дежурства

`settings.DUTY_MODE`: `"parse"` — только чтение (ордера не ставятся),
`"averaging"` — боевой торговый цикл (реальные ордера). Неизвестное или
отсутствующее значение безопасно откатывается в `"parse"`
(`modules/utils/modes.py`, `get_duty_mode`). Одна итерация `averaging` — это ОДИН
проход боевой стратегии (`trade_delayed_orders_strategy(..., max_iterations=1)`),
а не копия логики (`modules/duty_trade.py`).
