## 0. Замороженные решения

1. Репозиторий **public**. Причина: бюджет 0 ₽; private Free (2000 мин/мес) не покрывает дежурство; Pro/VPS отвергнуты владельцем. Public + обычный исполнитель = бесплатно и безлимитно.
2. Режим — **бесперебойное дежурство, как в ChatSum**: короткие запуски по расписанию образуют эстафету, в каждый момент один ведущий ведёт торговый цикл, остальные запуски — ожидающие. Зазоров между вахтами нет по построению (перекрытие запусков — дизайн, а не авария).
3. Каденс: cron **`7,19,33,46,58 * * * *`** (UTC, явный список минут). Причина: мимо пика начала часа (`:00–:05`, задержки и потери тиков прямо признаны в доках платформы) и мимо круглых минут (`:15/:30/:45` — стадный выбор, гипотеза, не замер). Зазоры 12–14 минут плюс шов 9 минут на границе часа. Старое обоснование «11 взаимно просто с 60, поэтому тики дрейфуют» — ошибка: расписание привязано к стенным часам, `*/11` сидит на фиксированных минутах, а не блуждает (исправлено в ChatSum 10.10). Ровные 10/15/30 брать запрещено.
4. Задание `timeout-minutes: 355` (потолок платформы 360; наш топор падает раньше и предсказуемо). Внутренний вотч ведущего **330 минут (19800 секунд)**. Бюджет: `330 (вотч) + 15 (хвост) + 1 (установка) = 346 ≤ 355`, запас 9 минут. Формула строгая, см. §2. Хвост 15, а не 10: патология ChatSum (~24 минуты перерасхода из стека «таймаут × повторы × ротация») один раз не покрылась хвостом 10.
5. **`concurrency` в workflow нет.** Перекрытие запусков — основа дизайна; арбитраж «кто ведущий» делает протокол дежурства (§1), а не очередь платформы. `cancel-in-progress` любого вида запрещён (убивает перекрытие).
6. Секреты только через env/Secrets. Ключи — ключи Hyperliquid **без права вывода**. Никогда не печатать секреты/ключи/токены в журнал (репо public, журналы видны всем). Вывод без буфера (`PYTHONUNBUFFERED=1`), иначе журнал отстаёт от реальности на минуты.
7. `pandas + numpy + openpyxl` **удалены полностью** (выполнено: коммит «migrate from Excel to CSV»). Статистика — `hype_stat.csv` через stdlib-`csv`, тот же набор колонок. Торговые решения excel не читают (читают биржу + состояние).
8. Кап «не стартовать работу у дедлайна» — **решение «нет», а не «потом»** (владелец ChatSum отклонил явно): хвост в бюджете существует именно для того, чтобы начатая итерация доработала; запрет стартовать превращает покрываемый перерасход в регулярное простаивание. Хвост работает по назначению.

## 1. Архитектура дежурства (перенос ChatSum целиком)

Каждый тик расписания стартует запуск. Запуск подключается к бирже, читает ветку `state` и либо становится ведущим (никого живого нет), либо уходит в ожидающие (дежурит рядом, готов подхватить). Ведущий ведёт торговый цикл до конца своего вотча, за ~минуты до дедлайна пишет `retiring` — свежий ожидающий подхватывает мгновенно, без зазора.

### 1.1. Ветка `state` (через интерфейс содержимого файлов GitHub, Contents API)

Отдельная долгоживущая ветка `state` (создаётся один раз вручную, пустым коммитом; дальше её трогают только код дежурства и финальный шаг workflow). Файлы:

| Файл | Содержимое (для hype) | Кто пишет |
|---|---|---|
| `state.json` | метки сверенных слотов/действий (`ключ: дата`, см. §4), `last_run_utc`, курсоры ротации и счётчики ошибок (семантика «побеждает большее», §1.3) | ведущий (ритмом стука сердца) + финальный Persist-шаг |
| `leader.json` | `run_id`, `ready` (false→true), `heartbeat_utc`, `watch_started_utc`, `retiring` (bool) | ведущий |
| `standby.json` | общий файл ожидающих: `run_id`, `heartbeat_utc` (последний активный ожидающий; «побеждает свежайший») | ожидающие запуски |
| `work.json` | `run_id`, `last_work_utc` — маркер «работа движется» (дёргается каждую итерацию ведущего) | ведущий |

Почему не вложения и не кэш: вложения/кэш привязаны к запуску и недоступны из другого запуска; ветка через Contents API — единственное общее постоянное место, доступное любому запуску без сторонних сервисов.

### 1.2. Протокол ведущий ↔ ожидающий (все числа строгие, менять только с владельцем)

- **Заявка (claim):** проверка-then-запись флага, побеждает последний записавший + один повтор при споре версий. Новый запуск заявляет `ready: false`, и только после успешного подключения к бирже (и первичного разбора!) ставит `ready: true`. Запуск, не достучавшийся до биржи, ведущим выглядеть не должен никогда.
- **Новичок при живом ведущем** → цикл ожидающего: без торговли, только чтение флага каждые ~30 секунд + собственный стук сердца в общий `standby.json`. Старый ожидающий уступает свежайшему («побеждает свежайший» — подхватывает обычно запуск возрастом ≤14 минут, правления остаются длинными).
- **Уступка:** ведущий уступает только живому + готовому + строго более новому ведущему; равное время старта → побеждает больший `run_id` (иначе уступят оба и дежурство останется без ведущего до следующего тика).
- **Подхват (promotion):** флага нет, стук сердца протух (старше `LEADER_STALE_SEC=300`), или ведущий `retiring` — подтверждается `PROMOTE_CONFIRM_READS=2` последовательными чтениями (защита от флэпа на одном медленном ответе).
- **Чистая ротация:** ведущий у дедлайна пишет `retiring` + отправляет → ожидающий подхватывает мгновенно, зазор — секунды. Это норма, к которой стремимся; убийство по лимиту времени — авария (см. §2).
- **Зависший ведущий (клин, wedge):** стук сердца отвечает «процесс жив», `work.json` — «работа движется» (дёргается каждую итерацию). Сердце свежее, но маркер того же `run_id` протух дольше `WORK_STALE_SEC=900` (15 минут) → takeover после тех же 2 подтверждающих чтений. Нет маркера (старый код) / чужой `run_id` / метка из будущего → takeover по этому основанию запрещён.
- **Наследование дедлайна (критично, оплачено двумя убитыми ведущими 05.10):** подхвативший ожидающий ведёт ОСТАТОК собственного вотча (считается от старта своего запуска, не от момента подхвата), а не полный вотч заново. Иначе новый дедлайн переживает задание — ротация умирает убийством платформой. Остаток ≤0 → одна полезная итерация, затем `retiring`.
- **Раздвоения** разрешаются правилом «побеждает новейший»; дубли ордеров гасятся сверкой перед постановкой (§5) — параллель не страшна, если каждая постановка предварена сверкой.

Имена-образцы из ChatSum (`run_once.py`, искать по имени, не по номеру строки): `new_leader_doc`, `leader_is_live`, `leader_should_yield`, `standby_should_promote`, `work_is_wedged`, `leader_watch_seconds`, `_leader_startup`, `_run_leader_loop`, `_run_standby_loop`, `_heartbeat_loop`, `_watch_cleanup`, `run_watch`.

### 1.3. Слияние состояния — один инвариант

Слияние местного и удалённого `state.json` — **объединение, никогда пересечение**: метки — свежайшая дата на ключ, счётчики — большее число (местное значение не должно откатывать чужой прогресс), `last_run_utc` — большее. Протухшие счётчики чистятся (окно 3 суток).

Запись: прочитать → слить → записать → при споре версий один повтор. Затем **проверка записи**: перечитать ветку, убедиться, что все местные метки на месте; расхождение → ещё одна запись + громкий `🚨` в журнал (растяжка на случай немой потери записи: утром 04.10 журнал показал «5× выполнено», а в ветке осела 1 метка, без ошибок, при одном писателе). Запуск никогда не выходит с ненулевым кодом из-за проблем состояния — в худшем случае местный файл увозит финальный `Persist state`-шаг workflow.

Очистка/выход ведущего: подтягивание-слияние ПЕРЕД сохранением/отправкой — молчаливый ожидающий или уступающий ведущий пишут только надмножество, никогда не затирают чужой прогресс.

Образцы: `merge_states`, `merge_completed`, `merge_counters`, `pull_state_best_effort`, `push_state_best_effort`, `_verify_push`, `_flag_claim`/`_flag_read` через Contents API (`GITHUB_API_URL`/`GITHUB_REPOSITORY`/`GITHUB_TOKEN`).

### 1.4. Самодиагностика зазоров (ловит аварии минутами, а не днями)

Новый ведущий ДО заявки читает последний чужой стук сердца (ведущий+ожидающие, свой `run_id` исключён). Тишина дольше `GAP_WARN_SEC=240` → предупреждение владельцу в связь с длительностью и временем последнего стука. Ниже порога — только строка в журнал. В ChatSum первый же варнинг подтвердил зазор 10–12 минут секунда в секунду с криминалистикой по ветке — метод доказан боем.

### 1.5. Маяк дежурства в канале связи (решение владельца 13.10)

Одно сообщение, две строки: `heartbeat ДД.ММ ЧЧ:ММ` + `next leader: ДД.ММ ЧЧ:ММ` (время местное, московское). Новый ведущий при заступлении подхватывает последний маяк поиском (максимальный номер среди своих сообщений с префиксом, глубина 50) и правит его каждый 5-й тик стука сердца (120с × 5 = 10 минут); нечего подхватить или правка упала (удалён вручную) — один перепост. Номер сообщения только в памяти (в `leader.json` не класть, иначе утечёт в общий флаг). Ожидаемый конец вахты считает цикл ведущего из своего дедлайна — это ориентир передачи, не гарантия: при потерях тиков фактический преемник встанет позже. Ожидающий ничего не пишет (нет торговли), на время дыры маяк честно протухает. Закрепляет владелец вручную. Для торгового цикла безвреден (разбор → пропуск).

## 2. Каденс и бюджет времени

### 2.1. Почему явный список `7,19,33,46,58`

Расписание привязано к стенным часам: `*/11` сидит на фиксированных минутах (`:00`, `:11`, …), а не блуждает — старая запись про «11 взаимно просто с 60, тики дрейфуют» была неверна и исправлена в ChatSum 10.10. Явный список держит запуски мимо пика начала часа (`:00–:05`, факт из доков платформы: задержки и потери) и мимо круглых минут (`:15/:30/:45` — стадный выбор, гипотеза, не замер). Зазоры 12–14 минут плюс шов 9 минут на границе часа. Частота ~5 в час может прореживаться платформой (замер канарейки на `*/11`: рождения раз в 2.5–9.7 часа, §15) — зазоры закрывают подхват (§1.2) и предупреждения о дырах (§1.4). Порог предупреждений держать чувствительным (240 секунд): при рваном покрытии это монитор дыр, а не шум.

### 2.2. Формула бюджета (нарушение = убийства, доказано)

```
вотч + хвост + установка ≤ timeout-minutes, запас ≥ 5 мин
```

- **Установка** = выгрузка + установка Python + `pip install`. Замеряется по первым запускам из журналов (~1 минута с кэшем pip; холодный кэш после смены `requirements.txt` — дольше). Удаление pandas (§0.п7, выполнено) ускоряет и холодную установку.
- **Хвост** = время, на которое одна начатая итерация может наехать на внутренний дедлайн. Дедлайн проверяется *между* итерациями, стартовавшая итерация всегда дорабатывает целиком. У ChatSum допущение «хвост 10» один раз не покрыло патологию (~24 минуты: стек таймаут×повторы×ротация) — запуски были убиты ровно на минуте лимита, все здоровыми посреди цикла.
- **Наши числа:** `330 + 15 + 1 = 346 ≤ 355`, запас 9 минут. Хвост 15 покрывает итерацию (секунды-минуты, см. §5) многократно. Если средняя установка из журналов превысит 3 минуты — уменьшить вотч, а не надеяться.
- **Подпись убийства:** `conclusion: cancelled` с длительностью ≈ `timeout-minutes` («ровно 355» — это усечение убийством, а не длительность зависания). Любой такой запуск — разбор бюджета, а не «перезапустить и посмотреть».
- **Метод контроля:** держать числа комментарием в yml и assert'ом в тестах дежурной логики (у ChatSum — `test_timeout_budget`: парсит workflow простыми шаблонами без зависимостей и утверждает неравенство).

## 3. Workflow (`.github/workflows/bot.yml`, создать на шаге лестницы §10, не раньше)

Причина откладывания: файл расписания, попав в главную ветку, сразу начинает дежурство в проде. Создавать только когда код проходит ручной запуск в режиме разбора (§10.п1). До этого — только док и дежурный слой без расписания. Цель — не получить торгующий прод раньше готовности, причина — планировщик подхватывает главную ветку за минуты, следствие — сырой workflow торгует на реальные деньги.

Образец — по боевому `ChatSum/.github/workflows/summarize.yml` (имена адаптированы под hype):

```yaml
name: Hyperliquid Bot Duty
on:
  # Явный список минут (§2.1): мимо пика :00–:05 и круглых минут.
  # Зазоры 12–14 мин + шов 9 мин; дыры ловит подхват + предупреждения.
  schedule: [{cron: '7,19,33,46,58 * * * *'}]  # UTC
  workflow_dispatch:  # ручной запуск участвует в дежурстве как обычный
    inputs:
      poll_interval:
        description: 'Пауза между итерациями в --watch, сек (по умолч. 60)'
        required: false
        default: '60'
      watch_seconds:
        description: 'Длительность цикла --watch, сек (по умолч. 19800 = 5.5 ч)'
        required: false
        default: '19800'
permissions: {contents: write}  # нужно: ветка state пишется через API (осознанное исключение)
# concurrency НЕТ — перекрытие запусков является дизайном (§0.п5)
jobs:
  duty:
    runs-on: ubuntu-latest
    timeout-minutes: 355  # потолок 360; бюджет §2.2 в комментариях: 330 + 15 + 1 = 346
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: '3.11', cache: 'pip', cache-dependency-path: 'requirements.txt'}
      - run: pip install -r requirements.txt
      # state.json — ВО ВНЕ рабочего дерева ($RUNNER_TEMP), чтобы несохранённый
      # файл не спорил с переключением веток при Persist. Выгрузка по умолчанию
      # не создаёт ссылку origin/state — нужен явный адрес ветки.
      - name: Fetch state
        run: |
          git fetch --depth=1 origin +refs/heads/state:refs/remotes/origin/state 2>/dev/null || true
          git show origin/state:state.json > "$RUNNER_TEMP/state.json" 2>/dev/null \
            || echo '{}' > "$RUNNER_TEMP/state.json"
      - name: Run duty
        env:
          BOT_RUNTIME: github_actions
          BOT_POLL_INTERVAL: ${{ github.event.inputs.poll_interval }}
          WATCH_SECONDS: ${{ github.event.inputs.watch_seconds }}
          STATE_PATH: ${{ runner.temp }}/state.json
          PYTHONUNBUFFERED: '1'  # иначе журнал отстаёт от реальности на минуты
          DB_ENCRYPTION_PASSWORD: ${{ secrets.DB_ENCRYPTION_PASSWORD }}
          WALLETS_DATA: ${{ secrets.WALLETS_DATA }}
          TG_BOT_TOKEN: ${{ secrets.TG_BOT_TOKEN }}
          PROFIT_BOT_TOKEN: ${{ secrets.PROFIT_BOT_TOKEN }}
          TG_USER_ID: ${{ secrets.TG_USER_ID }}
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          GITHUB_REPOSITORY: ${{ github.repository }}
        run: |
          echo "::add-mask::${{ secrets.WALLETS_DATA }}"
          echo "::add-mask::${{ secrets.DB_ENCRYPTION_PASSWORD }}"
          echo "::add-mask::${{ secrets.TG_BOT_TOKEN }}"
          echo "::add-mask::${{ secrets.PROFIT_BOT_TOKEN }}"
          # только цифры, иначе дефолты duty.py (защита от injections);
          # пустая строка от расписания иначе проскочила бы в argparse как ''.
          BOT_POLL_INTERVAL="${BOT_POLL_INTERVAL:-60}"
          case "$BOT_POLL_INTERVAL" in ''|*[!0-9]*) BOT_POLL_INTERVAL=60 ;; esac
          WATCH_SECONDS="${WATCH_SECONDS:-19800}"
          case "$WATCH_SECONDS" in ''|*[!0-9]*) WATCH_SECONDS=19800 ;; esac
          python -m modules.duty --watch --poll-interval "$BOT_POLL_INTERVAL" --watch-seconds "$WATCH_SECONDS" < /dev/null
      - name: Persist state  # финальный сейв: убийство заканчивается сейвом
        if: always()  # ALWAYS, не !cancelled() — иначе убийство = потеря меток
        run: |
          # При первом запуске checkout --orphan НЕ очищает дерево —
          # нужен read-tree --empty, иначе весь код попадёт в ветку state.
          git config user.name "hype-bot"
          git config user.email "hype-bot@users.noreply.github.com"
          if git fetch --quiet --depth=1 origin +refs/heads/state:refs/remotes/origin/state 2>/dev/null; then
            git checkout -B state origin/state
          else
            git checkout --orphan state
            git read-tree --empty
          fi
          # ветка state содержит только state.json
          cp "$RUNNER_TEMP/state.json" state.json
          git add -f state.json
          git commit -m "state: $(date -u +%Y-%m-%dT%H:%M:%SZ)" || true
          git push origin state || {
            echo "non-fast-forward (гонка) — rebase и повторный push"
            git pull --rebase origin state || true
            git push origin state || true
          }
      - uses: actions/upload-artifact@v4
        if: always()  # убитые запуски тоже оставляют журналы (криминалистика §6)
        with: {name: bot-logs, path: hyperliquid_bot.log}
```

Отдельный редкий запуск полного сброса (режим Cancel, cron раз в сутки + ручной, лимит 10 минут): в дежурстве не участвует, флаг не трогает, работает напрямую с биржей. Метки своих действий в `state.json` пишет (чтобы ведущий видел, что сброс был).

## 4. Состояние между запусками

Источник истины по ордерам и балансам — **биржа**: каждая вахта начинается с полного разбора. Файлы `databases/*`, `*.csv`, `*.log`, `input_data/` эфемерны (умирают с машиной) — это принято; ничего из них в git не коммитить (уже в `.gitignore`).

Но часть бывшего «местного» состояния переживает смерть только через ветку `state`:

- Детекция исполнений после рестарта — вести в `state.json` как метки/счётчики, а не принимать потерю. Потеря допустима лишь как деградация: первая итерация вахты восстанавливается сверкой с биржей.
- Курсоры ротаций/счётчики ошибок — в `state.json` с семантикой «побеждает большее» (§1.3): местное значение никогда не откатывает чужое.
- `hype_stat.csv` — по возможности: дописывается местно, прикладывается вложением; сквозная история не требуется (торговые решения его не читают).

## 5. Итерация ведущего (каждые ~60 сек внутри вахты)

Строго в этом порядке (дешёвое и защитное — раньше, дорогое и необратимое — позже, объём — ограничен):

1. **Разбор** — балансы + открытые ордера + цена BTC. Только чтение, один проход. Постановки только после полной сверки (см. п.4).
2. **Мягкий сброс** — снимать **только** устаревшее/осиротевшее (тейк без покупки, дубли уровня покупки без подтверждённого тейка; паузу уровня 600 секунд оставить). Полная зачистка всех ордеров в этом цикле **запрещена**.
3. **Сверка усреднения** — доставить недостающие лимиты покупки / тейки / пирамидинг по правилам стратегии. Перед КАЖДОЙ постановкой — сверка «такой ордер уже висит» (защита от дубля при повторе и при раздвоении — параллель не страшна, если сверка перед каждой постановкой). После постановки — записать номер ордера в журнал (криминалистика).
4. **Граница итерации:** объём постановок на итерацию ограничен (лучше недоставить один уровень за 60 секунд — доставит следующая итерация, чем раздуть итерацию до десятков минут и наехать хвостом на дедлайн). Худшая задержка реакции ≈ длительность одной итерации.

Почему шаг именно 60 секунд (не меньше): (а) открытый интерфейс Hyperliquid ограничивает частоту — опрос каждые 10–20 секунд часами упирается в 429/бан; (б) итерация сама длится секунды — при паузе 10 секунд нагрузка почти непрерывная плюс спам журналов; (в) сетка с шагом 200 долларов не требует тиковой реакции — ордера уже стоят на бирже; (г) интервал — переменная окружения (`BOT_POLL_INTERVAL`), не константа.

Дедлайн вотча проверяется вверху каждой итерации; стук сердца ведущего — **отдельной фоновой задачей** (не раз в N итераций!). Урок ChatSum: стук по итерациям замерзал во время длинных задач — ведущий выглядел мёртвым посреди работы и получал раздвоенного конкурента. Стук должен жить на ожиданиях ввода-вывода, а не в теле цикла. Маркер работы дёргается каждую итерацию.

`settings.py` (торговые параметры) внутри длинной вахты протухает: обновление настроек из главной ветки каждые ~10 минут (аналог 600 секунд из ChatSum; только чтение, дерево не трогается, ошибка сети — пропуск без падения).

## 6. Наблюдаемость: минимум, без которого убийства немы

1. **Границы вахты в журнале.** Первая строка — `shift start: run_id, время, сводка (балансы, число ордеров)`; последняя — `shift complete: итераций N` — или `retiring` при передаче. Отсутствие второй при `conclusion: cancelled` = подпись убийства. У ChatSum отсутствие `retiring` + свежий стук сердца за 40–90 секунд до смерти доказали «убит здоровым», а не «завис».
2. **Вложение журналов при любом исходе** (`if: always()`, §3). Без этого убийство не расследуется — исполнитель умирает вместе с машиной.
3. **Сигналы здоровья снаружи:**
   - список запусков — взгляд на итог: любой `cancelled` ≈ лимит времени расследуется по §2.2.
   - Оповещения в связь только об отклонениях: ошибки интерфейса/разбора, повторные `cancelled`, ордер не встал дважды подряд, предупреждение о зазоре (§1.4), маяк (§1.5). НЕ слать сводку каждую вахту (130 сообщений/сутки — спам, отучает читать; тишина = здоровье).
   - Маски секретов (`::add-mask::`, §3) + правило: секреты не коммитить, не печатать, не показывать. Здесь цена нарушения выше: репозиторий public.
4. **Пустые итерации прореживать** (печать каждой 20-й тихой итерации, занятые — всегда), иначе журнал тонет в мусоре, а важные строки теряются.

## 7. Дисциплина внешних вызовов

Патология ChatSum (~12 минут на один кусок, потом ~24 минуты перерасхода) сложилась из стека «таймаут HTTP × повторы × ротация × повтор». Перенос дословно:

- Каждый HTTP-вызов к бирже — с явным таймаутом. Нет таймаута = висящая итерация = висящая вахта = убийство.
- Повторы на итерацию — не более 2–3 попыток суммарно, затем итерация пропускается до следующей минутной. Следующая итерация повторит — это и есть устойчивость, а не бесконечный долбёж внутри одной.
- Быстрый отказ относится к итерации, не к вахте: одна пропущенная минута безвредна, зависшая вахта — потеря слежения за сеткой.
- Честная оценка времени действий в журнал (сколько заняла итерация/постановка): без замеров хвост не посчитать, а без хвоста нет бюджета (§2.2).

## 8. Секреты: метод доставки и хранения

- Доставка — только скриптом `scripts/push_hype_secrets.sh` (читает местные файлы, кладёт в Secrets через `gh`, значения не печатает — только имена и длины, есть пробный прогон без записи). Руками через веб — только в крайнем случае.
- Приватные ключи кошельков и пароли — в **Secrets** (не Variables): `WALLETS_DATA`, `DB_ENCRYPTION_PASSWORD`, токены. Проверить размер `WALLETS_DATA` (лимит секрета 48 КБ): не влезет — разбивать на части `WALLETS_DATA_1..N` со склейкой в загрузчике.
- Права workflow — минимальные, но с записью (нужна ветка `state`): `permissions: {contents: write}`. Это осознанное исключение из наименьших прав, записать комментарием.
- Ключи Hyperliquid без права вывода (§0.п6) — чтобы компрометация исполнителя не стоила средств.
- Проверки входа до работы (быстрый отказ, не молчаливый обход): `WALLETS_DATA` задан и разбирается, пароль открывает базу (см. §9.п2), иначе — ошибка и выход, а не интерактив.

## 10. Лестница первого запуска (порядок ввода в прод)

Каждый шаг — минимум 2–3 чистые вахты (`conclusion: success` + строка `shift complete`) подряд. Файл `.github/workflows/bot.yml` из §3 создавать только на шаге 2 (до этого дежурства в проде нет — и это правильно):

1. Ручной запуск в режиме разбора (`workflow_dispatch`, `BOT_MODE=5`, вотч 10 минут): проверяются секреты, дешифровка базы, цикл, тайминги, вложения — без постановки ордеров.
2. Cron в режиме разбора: сутки дежурства только для чтения — проверка ротаций (`retiring` в журналах, зазоры в секундах, предупреждений нет), бюджета установки, механики стук/ожидание. Торговли нет, риск нулевой.
3. Ручной запуск усреднения (1 вахта) под наблюдением: первые постановки.
4. Cron усреднения: штатное дежурство. Первый `cancelled` ≈ лимит времени — стоп и разбор по §2.2, а не «перезапустить и посмотреть».

## 11. Приёмка

- `BOT_RUNTIME=github_actions ... python main.py < /dev/null` местно: без терминала, завершается сам, exit 0.
- В журнале нет секретов (проверить отсутствие значений `WALLETS_DATA`, ключей, токенов даже частично).
- `pip install` без pandas/numpy/openpyxl; `hype_stat.csv` создаётся и дописывается.
- Два ручных запуска подряд не ставят дублей (второй видит ордера первого — сверка §5).
- Cron-запуски зелёные (`success`), в журналах `retiring` на ротациях, зазоры — секунды; вложение журналов приложено даже у убитых (`if: always()`).
- Маяк в канале связи правится каждые ~10 минут, при дыре честно протухает.
- Тесты дежурной логики зелёные (§9.п9).

## 12. Известные ограничения (не чинить, принять)

Джиттер старта расписания ±2–5 минут; после инцидентов платформы — десятки минут (факт ChatSum: 72 минуты), опоздавший запуск ужимается наследованием дедлайна (§1.2), отставшие тики встают следующими — отставание рассасывается само. Но главное ограничение — см. §15: планировщик молча роняет большинство тиков, рождения идут раз в часы. Отключение расписания после 60 дней без коммитов (лечится любым коммитом). Худший лаг реакции в штате ≈ шаг опроса (60 секунд) + джиттер — на порядок лучше сериализованных вахт. Реакция <10 секунд — только VPS, вне скоупа.

## 13. Инциденты ChatSum, сформировавшие §§0–8 (не переизучать)

1. Окно догона роняло слоты при зазорах шире окна → метки на ключ вместо окон. (У hype аналог: сверочные марки в `state.json`, а не «что успел за вахту».)
2. Короткий `timeout-minutes` убил запуск посреди анализа; недоделанное выглядело «повтором» → бюджет 355 (вотч + хвост + установка) + повторы внутри, а не рестартами.
3. Стук сердца раз в N итераций замерзал на длинных задачах → стук отдельной фоновой задачей. (Дословно перенесено в §5.)
4. Шторм догона (все немаркированные слоты подряд) морил голодом входящие → входящие первыми + кап объёма на итерацию. (Аналог — граница итерации в §5.)
5. Ночь трёх убийств (10-2026): вотч + установка не влезли в лимит; подхватившие ведущие начинали полный вотч заново и были обречены на убийство → наследование дедлайна (§1.2) + `Persist always()` (§3) + чувствительный порог предупреждений.
6. E2E-журнал «5× выполнено» при одной осевшей метке, без ошибок, один писатель, все пути union-safe → гипотеза: переходная несогласованность интерфейса при частых записах; лечение — проверка записи + `🚨` (§1.3). Не рецидивировало. Вывод для hype: проверка записи обязательна с первого дня, а не «когда-нибудь».
7. Миф про дрейф крона (10.10): «31 отмеряется от старта» опровергнут — расписание привязано к стенным часам; лечится явным списком минут (§2.1). В этом доке та же ошибка про `*/11` исправлена.
8. Лаг веб-журналов (~5 минут, 10.10): причина — блочная буферизация stdout при долгих молчаливых паузах; лечение — `PYTHONUNBUFFERED=1` (§3). Нагрузки не добавляет.

import os
from types import SimpleNamespace

def get_runtime_mode():
    explicit = os.getenv('BOT_RUNTIME', '').lower()
    if explicit in ('vps', 'github_actions'):
        return explicit
    return 'github_actions' if os.getenv('WALLETS_DATA') else 'vps'

    mode_id = os.getenv('BOT_MODE', '0')

        '5': {'type': 'module', 'soft_id': 5, 'text': 'Parse'},

    m = mode_map[mode_id]
    return SimpleNamespace(soft_id=m['soft_id'], type=m['type'], text=m['text'])

## 15. Реальность планировщика: тики роняются, дежурство — ведомая смертью (факты ChatSum, 02–10.10.2026)

Это самый важный раздел для понимания того, как дежурство живёт на практике, а не на бумаге. Числа ниже замерены в эпоху крона `*/11`; после перехода на список `7,19,33,46,58` их нужно перемерить за 2–3 суток по той же методе (интервалы рождений из списка запусков).

### 15.1. Рождения идут раз в часы, а не по крону

Крон `*/11` запрашивал ~130 тиков в сутки. Наблюдаемые рождения запусков: интервалы **2.5–9.7 часа, медиана ~4–5 часов** (вся история workflow — 28 запусков за 3 суток; рождений каждые 11 минут не было никогда). Причина — платформа: доки GitHub прямо признают задержки и молчаливые потери тиков под нагрузкой, 2026-й — череда инцидентов Actions. Со стороны репозитория всё чисто (крон верный, workflow active, файл на `main`) — чинить нечего, это внешний фактор.

### 15.2. Журнала тиков нет; есть только журнал выживших

Граница проходит ровно по факту создания запуска: тик → планировщик → [молчаливая потеря] → запуск → исполнитель → наш код. Несозданный запуск — несуществующий процесс: писать некому и некуда, поэтому журнала «тик сработал, но запуск не создан» нет ни внутри (процесса нет), ни снаружи (платформа его не отдаёт). Что есть:
- ✅ полный журнал ВЫЖИВШИХ: список запусков (время рождений), стуки сердца ожидающих/ведущего, коммиты ветки `state`;
- ❌ пустота вместо журнала потерь. Различить «сработал и потерян» vs «не сработал» снаружи нельзя — выглядят одинаково.

Следствие для исполнителя: любая диагностика планировщика строится только на рождениях. «Ждёт» в протоколе (§1.2) = уже запущенный процесс-наблюдатель (код работает, пишет стуки сердца, торговый цикл не ведёт). Новичок предшественника НЕ убирает: встаёт рядом в ожидание, подхватывает только на протухший/уходящий/мёртвый флаг; старый ожидающий уступает только *новому ожидающему* (сам завершается, увидев свежий run_id в общем файле).

### 15.3. Передача — ведомая смертью: цепочка, доказанная посекундно

Каждое рождение встаёт в ожидание, ждёт часами и подхватывает на смерти предшественника. Проверенная цепочка (UTC; длительности запусков 5:30 = ровно лимит 330 = убийство):
- рождение → ожидание ~2–3 часа → смерть ведущего убийством → подхват за ~5 минут → повтор.
- Чистая ротация через `retiring` без ожидающего рядом даёт зазор до следующего выжившего рождения (наблюдалось: 88 минут; предупреждение зафиксировало, подхват при рождении — мгновенный).

Отсюда операционное правило (согласовано с владельцем): **рождение дежурного не реже длины вотча (5.5 часа) = непрерывное покрытие**. Красивая retiring-передача требует ожидающего на месте; без него — запасной путь «зазор + подхват + предупреждение». Порог предупреждений держать чувствительным: при рваном покрытии это монитор дыр, а не шум.

### 15.4. Гипотеза «редкие кроны выживают лучше» — как проверять

Не менять дежурный крон вслепую (контраргумент: если потери случайные, редкий крон = меньше лотерейных билетов = риск дыр шире вотча). Метод проверки — канарейка: отдельный временный workflow с двумя кронами (список §2.1 + `*/31`), имя запуска фиксирует, какой крон родил запуск. Через 2–3 суток сравнить интервалы рождений по списку запусков, файл удалить. Только по данным решать о смене крона дежурства. (В ChatSum такой probe ставился как `.github/workflows/tick_probe.yml`.)
