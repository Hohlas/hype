# Аудит бота Hyperliquid (`main.py` + `modules/`)

Дата: 2026-09-23. Ревизия: `main` @ `41e6a2e`.
Предыдущее содержимое файла не использовалось (перезаписано пустым до начала аудита).

## 1. Объект и охват

Аудит объекта — исполняемый бот: `main.py` и импортируемые им модули `modules/*`.
Проверялись также документы, которые описывают этот код и на которые ссылаются выводы:
`docs/alg.md`, `docs/spec.md`, `README.md`.

Прочитано/проверено по коду:
- `main.py` — полностью.
- `modules/__init__.py`, `settings.py`, `retry.py`, `tg_tokens_loader.py`, `wallet_loader.py`,
  `utils/__init__.py`, `utils/utils.py`, `utils/modes.py`, `cancel_orders.py`, `parse_mode.py` — полностью.
- `modules/database.py`, `modules/hyperliquid_client.py` — полностью.
- `modules/delayed_orders_strategy.py` (2646 строк) и `modules/hyperliquid_browser.py` (1784 строки) —
  целевые пути: основной цикл, ветки входов, SET_TP, расчёт профита, подпись/создание/отмена ордеров,
  чтение балансов и истории, хелперы. Полный построчный разбор 4400 строк не выполнялся; выводы
  даны по фактически прочитанным участкам с указанием строк.

Проверяемые факты опираются на содержимое файлов; рантайм-подтверждение — `hyperliquid_bot.log`
(бот реально торговал: закрытые циклы с профитом, напр. строки 2026-09-23 16:06 и 17:18).

## 2. Итоговая оценка по критериям

- **Локальная корректность: НЕ ПРОЙДЕНО.** Есть подтверждённый критический дефект обработки ошибок
  инициализации (`main.py`), из-за которого одна неисправная учётка роняет весь прогон; и утечка
  секрета (Infura key) в репозиторий.
- **Целостность: НЕ ПРОЙДЕНО.** `requirements.txt` неполон (нет `pandas`/`openpyxl`) — чистовая установка
  ломает режим 0. Документация (`docs/alg.md`, `docs/spec.md`, `README.md`) системно рассинхронизирована
  с кодом (номера строк, версия, несуществующий `settings.py.example`).
- **Обоснованность подхода: условно приемлемая.** Основной торговый контур работает (подтверждено логом),
  но значительная часть кода — мёртвые/неподключённые ветки (режим 3, PostgreSQL-отчёты, набор функций),
  что искажает сопровождение и вводит в заблуждение при аудите.

## 3. Критичные замечания

### C1. `main.py` роняет весь прогон при ошибке инициализации аккаунта
- **Важность:** критично.
- **Место:** `main.py:87-103` (блок `finally` в `run_modules`).
- **Суть:** `hyperliquid_client` инициализируется как `None` (`main.py:59`). Если
  `initialize_account(...)` падает (например, невалидный приватный ключ — `hyperliquid_browser.py:68-70`
  делает `raise`), то в `finally` строка `if hyperliquid_client: await ...close_sessions()` безопасна,
  но далее **без проверки на `None`** вызывается
  `db.get_account_reports(key=hyperliquid_client.wallet_address, ...)` (`main.py:97-100`) и
  `hyperliquid_client.label` (`main.py:99`). Это `AttributeError`.
- **Доказательство:** `main.py:59,66-85,87-103`; `hyperliquid_browser.py:68-70`. `run_modules`
  запускается через `asyncio.gather(*[...])` без `return_exceptions=True` (`main.py:278-281`), поэтому
  исключение из `finally` всплывает в `runner` → `asyncio.run` → общий `except Exception` (`main.py:356`),
  завершая прогон всех аккаунтов.
- **Почему важно:** один битый ключ/прокси в списке убивает обработку остальных аккаунтов, а исходная
  причина маскируется вторичным `AttributeError`.
- **Исправление:** в `finally` обрабатывать `hyperliquid_client is None` (отдельная ветка для
  `module_data`/`group_data` без обращения к атрибутам клиента), либо возвращать/пробрасывать исходную
  ошибку без падения в `finally`. Дополнительно рассмотреть `gather(..., return_exceptions=True)`.

### C2. Секрет (Infura API key) закоммичен в репозиторий
- **Важность:** критично.
- **Место:** `settings.py:34` (`WEB3_RPC_URL = "https://mainnet.infura.io/v3/798bf9053eac4979995170257179c022"`).
- **Суть:** `settings.py` отслеживается git (`git ls-files` → `settings.py`), ключ присутствует в истории.
  В `.gitignore` строка `#settings.py` закомментирована (`.gitignore:60`), т.е. защита отключена.
- **Доказательство:** `git ls-files | grep settings` → `settings.py`; `git log --oneline -- settings.py`
  показывает коммиты; `git check-ignore settings.py` не игнорирует файл.
- **Почему важно:** утечка рабочего ключа провайдера; при публичном репозитории — компрометация.
- **Исправление:** вынести ключ в переменные окружения/локальный файл, заменить на плейсхолдер,
  ротировать скомпрометированный ключ, очистить историю (filter-repo/BFG). Раскомментировать
  игнор `settings.py` и завести `settings.py.example`.

## 4. Важные замечания

### I1. `requirements.txt` не содержит `pandas` и `openpyxl`
- **Важность:** важно.
- **Место:** `requirements.txt` (весь файл); импорт `import pandas` — `modules/delayed_orders_strategy.py:31`;
  `df.to_excel/read_excel` — `delayed_orders_strategy.py:681,686,884`.
- **Суть:** `pandas` (и Excel-движок `openpyxl` для `.xlsx`) не заявлены и не являются транзитивными
  зависимостями перечисленных пакетов. Чистая установка `pip install -r requirements.txt` пройдёт,
  но запуск режима 0 упадёт на импорте `modules.delayed_orders_strategy` (`hyperliquid_client.py:391`).
- **Доказательство:** `grep -Ei "pandas|openpyxl" requirements.txt` — пусто; `grep -rhoE "^import pandas"` —
  есть.
- **Почему важно:** заявленная README инструкция установки не приводит к работоспособному боту в режиме
  торговли.
- **Исправление:** добавить `pandas>=2.0` и `openpyxl>=3.1` в `requirements.txt`.

### I2. Отчёты в PostgreSQL фактически не работают: `DataBase.connect()` не вызывается
- **Важность:** важно.
- **Место:** `modules/database.py:46-63` (`connect`), `main.py:303` (`db = DataBase()`), вызовы
  `db.append_report` (`main.py:69`, `delayed_orders_strategy.py:1072`), `db.get_account_reports`
  (`main.py:97,149`).
- **Суть:** `connect()` нигде не вызывается (`grep` по `.connect()` в проекте — нет вызовов), поэтому
  `self.pool is None`. Тогда `execute()` (`database.py:77-79`) и `fetch()` (`database.py:88-90`)
  молча возвращают `None`/`[]`. Значит `append_report` ничего не пишет, `get_account_reports` всегда
  пуст, и финальная отправка отчётов `if reports:` в `main.py:104-105,156-157` недостижима.
- **Доказательство:** `grep -rn "\.connect()" main.py modules` — пусто; `database.py:77-79,88-90,119-139`.
- **Почему важно:** функциональность «отчёты аккаунта в БД», заявленная кодом и косвенно README
  («PostgreSQL опционально»), инертна; ошибки аккаунта через `append_report` теряются.
- **Исправление:** либо вызывать `await db.connect()` при старте и создать таблицу `reports`, либо убрать
  нерабочий путь и не создавать иллюзию персистентности.

### I3. `load_token_limits` принудительно перезаписывает минимальный размер `0.0001`, игнорируя API
- **Важность:** важно.
- **Место:** `modules/hyperliquid_client.py:100-114`.
- **Суть:** после разбора поля `minSz`/`minSize`/… (строки 100-107) значение безусловно перезаписывается:
  `min_qty = 0.0001` (строки 113-114, комментарий «Устанавливаем очень маленькое значение для тестирования»).

  («Получаем реальные лимиты от API»).
- **Доказательство:** `hyperliquid_client.py:110-114`.
- **Почему важно:** `check_minimum_order_size` (`delayed_orders_strategy.py:909-947`) проверяет `token_qty`

  отклоняться биржей (что и видно в логе: `Insufficient spot balance asset=10142`, строки 60-65).
- **Исправление:** убрать безусловную перезапись, использовать распарсенное значение с явным fallback.

## 6. Вопросы и неподтверждённые гипотезы

### Q1. «BTC — единственный актив на HL-споте» (`docs/spec.md:20`)
Неподтверждённое утверждение. В репозитории есть обращения и к другим спот-активам: `parse_mode.py:53`
(`["ETH","BTC","USDC","USDT"]`), маппинги `ETH: "@2"` (`delayed_orders_strategy.py:1471,1155`),
`hyperliquid_client.py` умеет `U{token}`. Формулировка, вероятно, означает «единственный актив,
закрывающий оба требования», но в буквальном чтении неверна. Требует уточнения формулировки.
(Если имеется в виду «единственный из спота, подходящий под оба критерия» — это оценочное суждение,
а не проверяемый факт.)

### Q2. Цена BTC берётся из перп-`allMids`, а не из спот-цены
Гипотеза (требует подтверждения владельцем). `get_token_price` (`hyperliquid_browser.py:540-613`)
перебирает ключи и первым совпадающим для `"BTC"` берёт `"BTC"` (перп-середина), а не `"BTC-SPOT"`/
`@142`; при этом бот торгует спот `UBTC/USDC`. Для расчётов прибыли/TP используется перп-мид как
прокси спот-цены. Насколько это допустимо — из кода однозначно не следует. Доказательство:
`hyperliquid_browser.py:580-594`. Не классифицирую как ошибку без подтверждения.

### Q3. `tick_size = 1` жёстко задан для спота
Гипотеза. `_create_spot_order` округляет цену шагом `1` (`hyperliquid_browser.py:1001,1008`), хотя
`self.btc_tick_size` загружается из `spotMeta` (`:784`). Для BTC-спота это, судя по логу, работает
(цены целые), но для других токенов было бы неверно. Так как торгуется только BTC, практического
дефекта сейчас нет. Доказательство: `hyperliquid_browser.py:784,1001,1008`.

### Q4. `get_all_orders_history` и лимит выборки
Вопрос. Запрос `userFillsByTime` идёт с `startTime` 10 лет назад без `limit` и последующей обрезкой
`[:limit]` (`hyperliquid_browser.py:1487-1493,1563`). Поведение зависит от серверного лимита HL (обычно
~2000 записей) и фильтрации по `coin`; при большом числе сделок «новая покупка» может не попасть в
выборку. Из кода однозначно не подтверждается — оставляю вопросом.
