## Замечания

### 1. [критично] Патч §2 («Замена интерактивного ввода пароля») чинит не тот метод

- **Место:** `docs/GithubActions.md:116-133` («Файл: `modules/database.py` — добавить поддержку DB_PASSWORD» в `set_password`); шаг 3 реализации (стр. 193).
- **Суть:** В торговом рантайме пароль запрашивает `get_password()`, а не `set_password()`. `set_password()` вызывается только из `create_modules()` (`database.py:193`), т.е. только при (пере)создании БД. Обычный запуск: `wallet_loader.get_wallet_modules` → `db.get_password()` (`wallet_loader.py:98`). `get_password()` (`database.py:104-171`) сначала пробует хардкодный дефолтный пароль (`:129`), а при его непригодности уходит в `while True:` с `input("> ")` (`:142-145`). После предлагаемого патча интерактивный ввод пароля в CI останется.
- **Доказательство:** `modules/database.py:84-102` (set_password), `:104-171` (get_password с input на :145), `modules/wallet_loader.py:98` (вызов get_password в рантайме), `modules/database.py:193` (единственный вызов set_password).
- **Почему важно:** заявленная проблема №2 из «Анализа проблем» фактически не решается планом; первый же не-дефолтный пароль уронит CI-ран по EOFError.
- **Исправление:** добавить чтение `DB_PASSWORD` в `get_password()` (пробовать env-пароль до дефолта и вместо интерактивного цикла); патчить `set_password` опционально. Обновить шаг 3 плана.

### 2. [критично] «Save state» через `actions/cache` с `if: always()` не сохранит кэш при упавшем джобе

- **Место:** `docs/GithubActions.md:53-58` (step «Save state», `uses: actions/cache@v4`, `if: always()`).
- **Суть:** Комбинированный `actions/cache` создаёт кэш на miss только при успешном завершении джоба. `if: always()` гарантирует лишь выполнение post-шага, но саму запись кэша не производит, если джоб смаркирован как failed (краш бота, превышение `timeout-minutes`). Именно в этих случаях сохранение состояния (`databases/`) важнее всего — между запусками теряется очередь/состояние стратегии.
- **Доказательство:** GitHub docs «Dependency caching reference»: «On a cache miss, the action automatically creates a new cache **if the job completes successfully**»; README actions/cache: «a new cache is automatically created provided the job completes successfully». Официальный рецепт сохранения при упавшем джобе — отдельный `actions/cache/save` с `if: always()`: раздел «Always save cache» в save/README.md (пример: `if: always() && steps.<restore>.outputs.cache-hit != 'true'`, `key: ${{ steps.<restore>.outputs.cache-primary-key }}`). В варианте плана используется комбинированный `actions/cache` — при failed-джобе запись не происходит.
- **Почему важно:** молчаливая потеря состояния при каждом аварийном ране; план §7 обещает «сохранение состояния между запусками», которое в happy-path-only варианте не выполняется.
- **Исправление:** заменить restore/save на `actions/cache/restore@v4` + `actions/cache/save@v4` (save с `if: always()` и `key` из `outputs.cache-primary-key` restore-шага), либо `upload-artifact`/`download-artifact` как альтернатива, уже упомянутая в §7.

### 3. [важно] Security-риск: кэш `databases/` содержит зашифрованные приватные ключи; пароль по умолчанию захардкожен в репо

- **Место:** `docs/GithubActions.md:34-39, 53-58, 182-187`.
- **Суть:** В кэш кладётся `databases/modules.json` — Fernet-шифртексты приватных ключей (`database.py:239-251`). Документ, обеспокоенный секретами в файлах (проблема №3), не анализирует, что Actions-кэш читаем шире, чем секреты. Плюс дефолтный пароль шифрования лежит в открытом коде: `database.py:95,129,150` (`"@karamelniy dumb shit encrypting"`).
- **Доказательство:** GitHub docs «Dependency caching reference» → «Best practices for using caches securely»: «Don't store sensitive information in a cache. Anyone who can open a pull request against your repository can read the contents of caches in the base branch. Don't write secrets, tokens, or credentials to a cached path». Репозиторий приватный (`gh repo view Hohlas/hype → visibility=PRIVATE`), что снижает (но не снимает) риск: любой с read-доступом может открыть PR и прочитать кэш base-ветки, а зная дефолтный пароль из кода — расшифровать ключи.
- **Почему важно:** компрометация приватных ключей торгового кошелька = прямой финансовый ущерб. Это единственный существенный риск плана, совершенно не разобранный (см. также «обоснованность подхода» ниже).
- **Исправление:** в документе явно зафиксировать ограничение: использовать только нестандартный `DB_PASSWORD` (и удалить/не использовать дефолт), рассмотреть `upload-artifact` c retention и ограничением доступа вместо кэша, либо отказаться от persist `modules.json` в Actions (пересоздавать БД из `WALLETS_DATA`, ключи — только из secrets). Минимум — добавить раздел «Риски» с этой угрозой.

### 4. [важно] Противоречие: `hype_stat.xlsx` обещан в состоянии (§7), но не покрыт путём кэша в YAML

- **Место:** `docs/GithubActions.md:37,57` (`path: databases/`) vs `:184-187` (список файлов состояния включает `hype_stat.xlsx`).
- **Суть:** `hype_stat.xlsx` лежит в корне репозитория, а не в `databases/` (`delayed_orders_strategy.py:667,821`: `stats_file = "hype_stat.xlsx"`). Шаг «Restore/Save state» с `path: databases/` его не сохранит.
- **Доказательство:** см. строки кода выше; .gitignore `*.xlsx` подтверждает, что файл в корне.
- **Исправление:** добавить `hype_stat.xlsx` в `path:` (cache поддерживает список путей/глобы) или убрать его из раздела 7.

### 5. [важно] Пропущен `databases/last_buy_timestamps.json` — единственный файл, чья persist-механика рассчитана на рестарты

- **Место:** `docs/GithubActions.md:9` (проблема №5) и `:184-187` (§7).
- **Суть:** Полный список состояния в `DataBase.__init__`: `modules.json`, `report.json`, `stats.json`, `last_buy_timestamps.json` (`database.py:22-25`). `last_buy_timestamps.json` документирован как переживающий рестарты (`database.py:262-265`) и используется стратегией для детекции филлов после перезапуска (`delayed_orders_strategy.py:1085`). План его не перечисляет. Кэш `path: databases/` подхватит его физически, но §7/§1.5 как спецификация неполны; при переходе на artifact-схему (упомянутую в §7) файл рискуют забыть. Замечание: `report.json` только создаётся/сбрасывается в `create_modules()` (`database.py:254`) и больше не пишется нигде (`grep report_db_name` даёт только database.py) — перечислять его в §7 не обязательно.
- **Исправление:** добавить `last_buy_timestamps.json` в §1.5 и §7.

### 6. [важно] Код `get_mode_from_env()` возвращает словари вместо объекта `Mode` — упадёт по AttributeError

- **Место:** `docs/GithubActions.md:103-114`.
- **Суть:** `main.py` обращается к атрибутам: `match mode.type:` (`main.py:236`), `mode.soft_id` (`main.py:238,247,251`). Snippet возвращает `{'type': ..., 'soft_id': ...}` — dict не поддерживает attribute access; замена `choose_mode()` на этот код крашит запуск.
- **Доказательство:** `main.py:236-251`; `Mode` — dataclass (`modes.py:14-26`), ожидаемый тип `choose_mode() -> Mode` (`modes.py:35`).
- **Исправление:** возвращать `Mode(soft_id=..., type='module', text=...)` или `SimpleNamespace`. Также стоит предусмотреть валидацию значения `BOT_MODE` (сейчас любое неверное значение молча сваливается в режим 0 — для торгового бота это risky default; лучше падать с явной ошибкой).

### 7. [важно] Нет защиты от параллельных запусков (concurrency) — два бота могут торговать одним кошельком

- **Место:** YAML варианта 1 (`docs/GithubActions.md:16-66`), вариант 3 (`:83-95`).
- **Суть:** `schedule` может запаздывать (GitHub гарантирует only «may»-запуск, пиковые нагрузки сдвигают cron), `workflow_dispatch` позволяет ручной запуск поверх работающего scheduled-джоба. Блокировки `address_locks` (`modules/__init__.py:24-36`) действуют только в рамках одного процесса; между раннерами (runner) дедупликации нет → гонка ордеров на один кошелёк.
- **Доказательство:** отсутствие `concurrency:` в YAML плана; `main.py` не содержит межпроцессной синхронизации.
- **Исправление:** добавить в документ обязательный `concurrency: bot-${{ ... }}` с `cancel-in-progress: false` (или `queue`) и пометкой, что это защищает и от workflow_dispatch.

### 8. [улучшение] Проблема №4 («бесконечный цикл main.py:233») — неточная атрибуция

- **Место:** `docs/GithubActions.md:8`.
- **Суть:** `while True` в `main.py:233` — это цикл меню: `runner()` при любом исходе возвращает `'Ended'` (`main.py:165-212`, единственная точка выхода `return 'Ended'` на `:212`), поэтому после `case "module"` происходит `break` (`:251`). Реальный «никогда не завершается» цикл для режима 0 — `delayed_orders_strategy.py:1150` (+ watchdog `:118-135`), что план корректно закрывает в §6. Для режимов 4/5 (`cancel_orders.py`, `parse_mode.py`) циклов нет — отработают и выйдут, §6 для них не нужен.
- **Исправление:** переформулировать: «бесконечный цикл стратегии Averaging (`delayed_orders_strategy.py:1150`)`; main.py:233 упомянуть как цикл меню, не проблема CI (при env-режиме он всё равно завершится после одного прогона)».

### 9. [вопрос] «Зависание в CI» от `input()` — локально проверяемое поведение отличается

- **Место:** `docs/GithubActions.md:10` («блокирующий input()... зависание в CI»), `:5-6`.
- **Суть/доказательство:** локально `input()` без TTY (stdin=/dev/null) бросает `EOFError` мгновенно, не виснет: `setsid -w python3 -c "input()" </dev/null` → `EOFError: EOF when reading a line`, exit=1. На GitHub-hosted раннере stdin шага — тоже не TTY, поэтому правдоподобный исход: не hang, а падение с EOFError (для `main.py:265` внутри try это ловится `except Exception` на `:284` и снова упирается в `input()` на `:286` → аварийный выход). Поведение раннера документально не подтверждено — это неподтверждённая гипотеза. Для `inquirer.prompt()` (проблема №1) поведение без TTY не проверялось вовсе.
- **Почему важно:** меняет только symptom (fail fast vs hang до timeout-minutes=30 → убитый джоб), не вывод: оба варианта ломают ран. Но в плане стоит писать точный ожидаемый симптом, чтобы шаг 7 («протестировать локально») интерпретировался верно.
- **Исправление:** заменить «зависание» на «падение с EOFError (или hang до timeout — зависит от stdin раннера)»; при локальном тесте (шаг 7) использовать `python main.py < /dev/null`.

### 10. [улучшение] Формулировка проблемы №3 и детали §3

- **Место:** `docs/GithubActions.md:7`, `:135-155`.
- **Суть:** (а) `tg_bot_tokens.txt` содержит токены Telegram-ботов, а не «приватные ключи» — терминологическая неточность; (б) `input_data/` уже в `.gitignore` (`input_data/*`), файлы не в git (`git ls-files`) — риск именно «секретов в файлах в CI-чекауте», которого в репо нет, стоило сформулировать как «секреты нужно передать в репозиторий для запуска в Actions» (checkout не содержит input_data/ → без env-фолбэка бот вообще не найдёт кошельки); (в) формат `WALLETS_DATA` не определён: в примере `json.loads(wallets_json)` — какой формат (список `label|addr|pk|proxy`-строк или массив объектов)? Должен быть зафиксирован в плане.
- **Исправление:** уточнить термины и добавить спецификацию формата env-секретов.

### 11. [улучшение] Имя `DB_PASSWORD` конфликтует с уже существующим сеттингом PostgreSQL

- **Место:** `docs/GithubActions.md:47,120-129` vs `settings.py:24`.
- **Суть:** `settings.DB_PASSWORD = "password"` — параметр (не используемой) PostgreSQL; env `DB_PASSWORD` план навешивает на пароль шифрования Fernet. Коллизия имён запутает и может привести к ложному ощущению «секрет уже настроен».
- **Исправление:** переименовать env в `DB_ENCRYPTION_PASSWORD` (и в YAML, и в §2).

### 12. [улучшение] Вариант 3: YAML-сниппет невалиден как единый файл; нет имён файлов

- **Место:** `docs/GithubActions.md:83-95`.
- **Суть:** Один snippet с `---` посередине и двумя корнями `name:` — это набросок двух workflow; как есть в один файл не разворачивается. План (шаги 1, «Создать .github/workflows/bot.yml») не говорит, что варианта 3 = два файла. Также `cron: '0 2 * * *'` назван «раз в день в 2:00» — верно, но стоит напомнить про UTC и про то, что `schedule` работает только на default branch (и может запаздывать).
- **Исправление:** показать два отдельных файла (`averaging.yml`, `cancel.yml`), добавить примечание «cron в UTC; schedule — только default branch».

### 13. [улучшение] Вариант 2: `timeout-minutes: 360` равен лимиту — нет запаса на корректное завершение

- **Место:** `docs/GithubActions.md:78`.
- **Суть:** GitHub убивает джоб ровно на 6h; без запаса `Save state` (пост-шаг) может не успеть, и состояние потеряно. §6 (`BOT_MAX_RUNTIME`) — правильное направление, но в варианте 2 env не показан.
- **Исправление:** `timeout-minutes: ~345` и/или `BOT_MAX_RUNTIME=330` в env, плюс явная ссылка на замечание №2 (save при always нужен `cache/save`).

### 14. [улучшение] Мелочи по YAML варианта 1

- Установку pip-зависимостей можно кэшировать (`cache-dir` в `setup-python@v5`), иначе каждый ран — полная установка (requirements.txt содержит компилируемые eth-account/pandas/openpyxl; на 30-минутном бюджете это съедает время). Не блокер, но стоит отметить.
- `actions/cache@v4` актуален и не деприкейчен (v5/v6 существуют, v1-v2 deprecated — README actions/cache), возражений нет.
- Раздел «Шаги реализации»: шаг 2 («убрать интерактивный ввод») фактически включает и замену режима, и input() — согласуется; шаг 8 (секреты) логично дополнить проверкой, что `.github/workflows/*.yml` и `settings.py` закоммичены (settings.py — в git, проверено `git ls-files`, конфликтов нет).

## Итог по критериям

- **Локальная корректность:** раздел «Анализ проблем» подтверждён по строкам (см. таблицу); неточности — замечания №8, №9, №10. Ключевые решения содержат две рабочие ошибки (№1, №2) и одну невалидную кодо-замену (№6).
- **Целостность:** YAML варианта 1 противоречит собственному §7 (№4) и неполному списку состояния (№5); §2 не закрывает заявленную проблему №2 (№1).
- **Обоснованность подхода:** выбор «периодический запуск + кэш состояния + env-секреты» в целом приемлем и лучше варианта 2 для CI; однако существенный риск (№3: кэш с шифроключами + дефолтный пароль в коде) не выявлен, риск параллельных запусков (№7) не учтён, альтернатива «пересоздавать БД из WALLETS_DATA каждый ран вместо persist modules.json» не рассмотрена — хотя она снимает сразу №3 и половину №5.
