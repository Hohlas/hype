# Аудит `docs/spec.md`

Дата: 2026-09-22
Объект: `docs/spec.md` (58 строк), репозиторий `/root/keys/hype`, ветка `main` (HEAD `f298396`).

## Резюме

Документ — обоснованный план реархитектуры спот-стратегии (Core 50% + Grid 50%, частичный TP + runner). Диагноз «сетка сдаёт позицию на `entry+STEP` и проигрывает холду в тренде» **подтверждается кодом**. Однако часть опорных цифр (§1: «15%», «$600»; §2) не соответствует текущему состоянию репозитория на ветке `main` (там `POSITION_SIZE_PERCENT=5`, `STEP=200`) и совпадает с настройками другой ветки `feature/lighter-exchange` (15%, 600). Также §5 ссылается на несуществующие документы (`PLAN.md`, `base-context.md`, `CHANGELOG`), а §2/§5.1 предписывают калибровку через `Parse`, которая в текущем коде невозможна (нет истории свечей/ATR/объёмов и бэктеста). Ниже — детали с доказательствами.

## Оценка по критериям

### 1. Локальная корректность
- Подтверждено кодом: TP целиком на `entry+STEP` (`delayed_orders_strategy.py:1059-1060`, `:648-655`); пирамидинг маркетом при `current > max_TP − STEP×AGGR`, `AGGR=0.5` (`:1803-1804`, `settings.py:10`); усреднение лимитом на `min_TP − STEP×2` (`:1645`); один buy-limit снизу (`:1653`, «Если нет BUY ордеров…», docstring `:11-16`); функция `calculate_usdc_amount_for_order` существует (`hyperliquid_client.py:30-53`), размер = % от доступного USDC (`get_available_balance`, `hyperliquid_browser.py:472`); Excel-колонки `USDC/BTC/Total Value` без разделения Core/Grid (`delayed_orders_strategy.py:294-297`); `find_matching_buy_trade` существует (`:113`); `spotMeta` в коде есть, но только для asset-ID (`hyperliquid_browser.py:707-725`, `hyperliquid_client.py:82`).
- **Ошибки/расхождения**: цифры «15%» и «$600» не соответствуют `main`; формулировка «STEP захардкожен» неверна (STEP — конфиг `settings.py`); «комиссия 0.0384%×2» не имеет подтверждения ни в коде, ни в документе.

### 2. Целостность
- Архитектура Core/Grid 50/50 внутренне согласована, метрика паритета (§4.3) формально корректна (`hold_benchmark = депо_старт / цена_старт × цена_сейчас`).
- Несогласованности: а) весь §2 (проверка «STEP $600 ≈ 0.4–0.6%») построен на недокументированной величине $600, которой нет в `main`; б) режимы Range/Trend имеют два конкурирующих триггера (пирамидинг при `current > max_TP − STEP×AGGR` срабатывает раньше триггера тренда «новые хаи» `current > max_TP`), взаимодействие не описано; в) §5.4 отсылает к несуществующим артефактам.

### 3. Обоснованность подхода
- Подход в целом состоятелен: консервативный Core держит позицию (лечит cash drag), Grid оставляет текущую тактику. Риски в §5 перечислены, но **неполны**: не описано, как работают триггеры `min_TP/max_TP` (они вычисляются только из resting sell-ордеров, `:1499-1502`), когда часть позиции становится runner’ом без висящего sell; нет механизма и источника данных для бэктеста (§5.2), которого в репозитории нет; нет метода ребаланса Core.

## Замечания

### 1. `важно` — §1, строки 9–12 и §2, строка 23: опорные цифры «15%» и «$600» не соответствуют текущему состоянию репозитория; источник не указан
- **Суть**: Документ утверждает «Каждый вход = 15% от доступного USDC» и «STEP=$600» как факты текущего поведения. В рабочем дереве (`main`): `settings.py:7 POSITION_SIZE_PERCENT = 5`, `settings.py:8 STEP = 200`, `version = "1.2.5"`. Эти цифры (15%, 600, version 1.2.7) совпадают только с веткой `feature/lighter-exchange` (`git show feature/lighter-exchange:settings.py`). Документ не указывает, какую конфигурацию/ветку он описывает.
- **Доказательство**: `rg -n "STEP|POSITION_SIZE_PERCENT" settings.py` → 200/5; `git show feature/lighter-exchange:settings.py | rg -n "STEP|POSITION_SIZE_PERCENT"` → 600/15; `hyperliquid_client.py:49-50` (размер = `settings.POSITION_SIZE_PERCENT`); ветки: `git branch -a` (`main`, `feature/lighter-exchange`).
- **Почему важно**: на этом построена диагностика §1 и решение §2 (проверка «STEP $600 ≈ 0.4–0.6%»; при STEP=200 расчёт дал бы ~0.13–0.2%, т.е. правило §2 уже требует перевода STEP в проценты — вывод меняется). Без указания конфигурации §1/§2 невоспроизводимы.
- **Исправление**: указать явно, какая конфигурация анализируется (ветка/значения `STEP` и `POSITION_SIZE_PERCENT`), либо привести оба варианта. Если документ описывает продовую конфигурацию на ветке lighter — сослаться на неё.

### 2. `важно` — §5.4, строка 56: ссылки на несуществующие документы
- **Суть**: «Доки: `PLAN.md` → новый этап…, `base-context.md` §5–6…, CHANGELOG `1.3.0`». В репозитории (все ветки) нет ни одного из этих файлов.
- **Доказательство**: `git ls-files | rg -i "\.md$"` → только `README.md`; `git ls-tree --name-only feature/lighter-exchange | rg -i "plan|context|changelog"` → пусто; `git log --all --oneline --diff-filter=A -- '*PLAN*' '*CHANGELOG*' '*base-context*'` → пусто.
- **Почему важно**: DoD-пункт невыполним как написан; `CHANGELOG 1.3.0` ссылается на версию, которой нет ни в одном `settings.py` (`main` — 1.2.5, `feature/lighter-exchange` — 1.2.7).
- **Исправление**: переформулировать как «создать PLAN.md, base-context.md и CHANGELOG (bump до 1.3.0)» либо удалить ссылки, если документы не ведутся.

### 3. `важно` — §2, строка 23 и §5.1, строка 53: калибровка через `Parse`-режим и `spotMeta` невозможна в текущем коде
- **Суть**: Предписано «через `spotMeta` + `Parse`-режим снять … объёмы, спред, ATR(1d/4h), долю времени в диапазоне vs тренде, частоту касаний `+STEP`». `parse_mode.py` выводит только балансы, позиции, активные ордера и текущие цены (`modules/parse_mode.py:9-64`); `spotMeta` используется только для получения asset-ID (`hyperliquid_browser.py:707-725`). Свечей/OHLC/ATR/объёмов/спреда в коде нет, бэктеста нет (`rg -in "candle|atr|volume|backtest"` → только упоминания в самом spec.md).
- **Доказательство**: `modules/parse_mode.py:17-64`; `modules/hyperliquid_browser.py:707-725`; grep по репозиторию не находит исторических данных.
- **Почему важно**: весь §5 «цифры из Parse, не с потолка» основан на инструменте, который эти цифры не даёт; без источника исторических данных (например, HL endpoint `/info` candles или внешний API) DoD-шаги 1–2 не выполняются.
- **Исправление**: указать конкретный источник данных (candles-эндпоинт HL, файл истории/экспорт) и инструмент расчёта ATR/доли времени; отметить, что Parse-режим нужно расширить или использовать внешние данные.

### 4. `важно` — §4, строки 36–43: не описано взаимодействие триггеров Range-пирамидинга и Trend-детектора
- **Суть**: Текущий пирамидинг срабатывает при `current > max_TP − STEP×AGGR` (AGGR=0.5), т.е. раньше нового хая. Предложенный триггер тренда «`current > max_TP` (новые хаи)» в монотонном росте почти никогда не сработает: сетка пирамидит за ~0.5×STEP до `max_TP`, сразу выставляет новый TP, и `max_TP` каждый раз «убегает» вверх. Тренд-режим сможет включиться только через вторую ветку триггера `current > MA(N)`. Приоритет/отношение триггеров и гистерезис не определены.
- **Доказательство**: `delayed_orders_strategy.py:1803-1809` (триггер пирамидинга `max_TP − STEP×AGGR`, AGGR из `settings`); spec.md:36 (триггер `current > max_TP`).
- **Почему важно**: без описания логики режимы могут не переключаться вовсе либо дёргаться на границе — цель §4 (захват тренда) рискует не достигаться.
- **Исправление**: задать явный порядок: тренд-режим включается по `current > MA(N)` (или по N новых хаёв), а `current > max_TP` — как под-условие/подтверждение; описать, как `min_TP/max_TP` пересчитываются в тренде, когда 50% входа продано, а runner держится без resting sell (`:1499-1502`).

### 5. `вопрос` — §1, строка 11: «Комиссия 0.0384%×2» неподтверждена
- **Суть**: В коде нет константы 0.0384; комиссии берутся из фактических сделок (fee/feeToken из trade history), а при отсутствии сделки — оцениваются как `filled_qty × STEP` минус buy/sell commission (`delayed_orders_strategy.py:1274-1351`). Опубликованные ставки HL-спота (Tier 0): taker 0.070%, maker 0.040% (база); 0.0384% не соответствует ни одной публичной ставке без оговорки о скидках. Кроме того, buy — маркет (taker), sell — лимит (maker), т.е. «×2 по 0.0384%» предполагает одинаковую ставку для обоих плеч, что обычно неверно.
- **Доказательство**: `rg -n "0\.0384"` по репозиторию → только в spec.md; `delayed_orders_strategy.py:1274-1351` (реальные комиссии из истории); внешние источники (docs HL Fees, 2026): spot taker 0.070%/maker 0.040% Tier 0.
- **Почему важно**: величина комиссий участвует в аргументе «комиссия ест STEP»; если число неверно, количественная оценка искажается (направление аргумента, впрочем, верно).
- **Исправление**: указать источник ставки (реальные филлы/логи, tier, скидки за стейкинг) или переформулировать качественно; различать taker/maker для buy/sell плеч.

### 6. `улучшение` — §1, строка 12: «STEP=$600 захардкожен под BTC» — неточно
- **Суть**: STEP не захардкожен в коде — это значение в `settings.py` (`delayed_orders_strategy.py:852 step = Decimal(str(settings.STEP))`). Реальная проблема — единый абсолютный STEP в долларах для любого токена, а не «захардкоженность».
- **Доказательство**: `settings.py:8`; `delayed_orders_strategy.py:852`.
- **Почему важно**: формулировка вводит в заблуждение при чтении диагноза (вывод «только BTC» обоснован, но аргумент «захардкожен» ложный).
- **Исправление**: «STEP — единый долларовый параметр в settings.py, не адаптируется под актив/ATR».

### 7. `улучшение` — §3, строка 29: «по построению даёт ≥~50% результата холда» — верхняя оценка, не гарантия
- **Суть**: Core покупается «лимиткой частями». В быстром росте часть лимиток не успеет исполниться → экспозиция < 50% → захват < 50% холда. В падении — наоборот, лимитки добираются ниже → экспозиция растёт на падающем активе.
- **Доказательство**: spec.md:29 (закупка частями, не в одну точку); `safe_place_order`/`place_order` — лимитный ордер исполняется только при касании цены.
- **Почему важно**: «≥~50% в любом тренде» — оптимистичная оценка; при её использовании как критерия §4.3 (Total ≥ 0.8–0.9×hold) возможно ложное ожидание.
- **Исправление**: уточнить «≈50% при полном заполнении Core; ниже при недозаполнении в быстром росте».

### 8. `улучшение` — §4, строка 40: два альтернативных правила трейлинга runner’а
- **Суть**: «трейлингом `STEP×2` **или** по `max_TP − STEP`» — две разные механики; выбор не зафиксирован (в §4.1 параметр только `TRAIL_STEP_MULT=2`).
- **Доказательство**: spec.md:40; spec.md:47 (в `settings.py` предлагается только `TRAIL_STEP_MULT`).
- **Почему важно**: неоднозначность при реализации и бэктесте.
- **Исправление**: выбрать одно правило (например, трейл на основе `max_TP − STEP` с фиксацией максимума) либо явно указать, что «или» — это два настраиваемых варианта с отдельными параметрами.

### 9. `вопрос` — Шапка, строка 3: «перпы (Lighter) заморожены — причина: funding» без подтверждения
- **Суть**: Утверждение о заморозке перпов и о том, что funding «убивает» долгую сетку, в репозитории ничем не подтверждено (нет анализа funding, нет документированного решения о заморозке). Само упоминание Lighter согласуется с существованием ветки `feature/lighter-exchange`.
- **Доказательство**: `git branch -a` → `feature/lighter-exchange`; в коде/истории нет расчёта funding для сетки (grep по funding → только spec.md).
- **Почему важно**: это обоснование ключевого решения «остаёмся на споте»; без цифр (реальная сумма выплаченного funding в долгих сетках) аргумент декларативен.
- **Исправление**: добавить количественное подтверждение (выплаченный funding/период, % от депо) либо пометить как гипотезу, подлежащую проверке на исторических данных.

### 10. `улучшение` — §5.3, строка 55: «Core покупается, Grid крутит, runner отрабатывает первый тренд без ручного вмешательства» — нет критерия прохождения шага
- **Суть**: Шаг 3 «живой прогон малыми суммами» не имеет измеримого критерия успеха/остановки (в отличие от §5.2, где критерий — метрика §4.3).
- **Доказательство**: spec.md:55.
- **Почему важно**: без критерия шаг не может быть признан выполненным в рамках DoD.
- **Исправление**: добавить числовой критерий (например, коррекция поведения относительно бэктеста ≤ X%, N полных циклов Grid без ошибок).

## Итог
- **Подтверждено кодом**: диагноз §1 (TP целиком на `entry+STEP`, пирамидинг маркетом, cash drag, уменьшение входов), параметры `AGGR=0.5`, `min_TP − STEP×2`, один buy-limit, «всё смешано в Excel», существование `find_matching_buy_trade`, `calculate_usdc_amount_for_order`, `spotMeta`/Parse.
- **Требует правок (важно)**: источник цифр «15%/600» (§1–2); несуществующие документы в §5.4; невозможность калибровки через Parse (§2/§5.1); неопределённое взаимодействие триггеров Range/Trend (§4).
- **Неподтверждённые гипотезы/вопросы**: ставка комиссии 0.0384% (§1); обоснование заморозки перпов funding'ом (шапка).
- **Критичных ошибок, меняющих вывод документа, не обнаружено**: направление решения (Core+Grid, частичный TP+runner) обоснованно и согласуется с логикой кода.
