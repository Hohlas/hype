# Spec: спот HL, только BTC, 50% Core + Grid с частичным TP

> Решение: остаёмся на споте Hyperliquid. Базовый актив — только BTC. Депо делится 50/50 Core/Grid. В тренд-режиме — частичный TP + runner с трейлингом. Отказ от перпов (ветка `feature/lighter-exchange`) — рабочая гипотеза: долгую усредняющую сетку убивает почасовой funding; численное подтверждение (фактический funding/период по истории ставок) — открытый пункт калибровки (§5.1), в репозитории данных funding нет.

## 1. Диагноз: почему текущая сетка проигрывает холду в тренде

Разбор `delayed_orders_strategy.py` + `client.calculate_usdc_amount_for_order`:

Конфигурация разбора: ветка `feature/lighter-exchange` (`settings.py`: `POSITION_SIZE_PERCENT=15`, `STEP=600`, `version 1.2.7`). На `main` значения другие (`5`, `200`, `1.2.5`) — долларовые выводы §1–2 масштабируются пропорционально, правило STEP% (§2) от конфигурации не зависит.

- Каждый вход = **15% от доступного USDC** (значение разбираемой конфигурации; механика — `settings.POSITION_SIZE_PERCENT` от доступного баланса, `modules/hyperliquid_client.py`). После входов USDC тает → следующие входы всё меньше. Экспозиция к BTC в тренде ~20–30%, у холдера — 100%.
- Каждый вход продаётся **целиком на `entry + STEP` ($600 в разбираемой конфигурации)**. В монотонном росте сетка «продаёт победителей слишком рано», деньги возвращаются в USDC и ждут следующего пирамидинга — **cash drag**.
- Пирамидинг (`current > max_TP − STEP×AGGR`, маркет) докупает снова мелко и снова сдаёт через +$600. Оборот большой, захват тренда маленький. Комиссии обоих плеч (вход — маркет/taker, TP — лимит/maker) дополнительно едят STEP; в коде основной путь — фактические fee из истории сделок, fallback — 0.0144% на плечо (`modules/delayed_orders_strategy.py`, расчёт profit); точные ставки — по tier аккаунта.
- `STEP=600` — единый долларовый параметр в `settings.py` (читается в `modules/delayed_orders_strategy.py:852`), не адаптируется под актив/ATR. Для других активов не годится — ещё один аргумент за «только BTC» сейчас.

Итого: в боковике сетка стрижёт STEP-купоны и выигрывает, в тренде — системно отстаёт, потому что **не держит позицию**.

## 2. Инструмент: почему BTC — ответ на «боковик либо не падает»

«Вечного боковика» не существует. Два требования, BTC — единственный актив на HL-споте, закрывающий оба приемлемо:

- **«Не падает» (не обесценивается навсегда):** BTC — максимальная капитализация/ликвидность на HL, наименьший риск −90%-без-возврата. Альты и мемы в боковике хороши, но на медвежке падают сильнее и часто не возвращаются — для сетки это смерть (мешок без TP). Low-cap — запрет.
- **«Болтается в боковике»:** BTC достаточно волатилен внутри дня/недели (ATR позволяет цеплять STEP ~0.4–0.6% от цены), а на старших ТФ регулярно пилит диапазоны. Боковик не ищем как свойство тикера навсегда — **настраиваем STEP под ATR BTC**, тренды переживаем за счёт Core.

Проверка перед внедрением. Источник — история свечей BTC-SPOT (candles-запрос к `/info` API HL — проверить покрытие, либо внешний экспорт; `Parse`-режим `modules/parse_mode.py` этого не даёт — только балансы/позиции/ордера/цены — поэтому для калибровки нужен отдельный офлайн-скрипт): объёмы, спред, ATR(1d/4h), доля времени в диапазоне vs тренде, частота касаний `+STEP` от входа. Правило: STEP% = STEP/цена; старт 0.5%; если фактический STEP% вне 0.4–0.6% — STEP переводится в проценты (`STEP_PCT`).

## 3. Новая архитектура: Core 50% + Grid 50%

Депо делится один раз, дальше контуры не смешиваются:

- **Core (50%, купи-и-держи):** при старте покупается на 50% депо (лимиткой частями, не маркетом в одну точку). Дальше **не продаётся по STEP вообще**. Докупка — только на глубокой просадке (опция, порог: −15–20% от средней Core) или ребаланс раз в N недель к 50%. При полном заполнении Core даёт ≈50% результата холда; при недозаполнении лимиток в быстром росте — ниже.
- **Grid (50%, текущая тактика):** работает на оставшихся USDC + своих BTC. Те же отложенные ордера: лимит вниз `min_TP − STEP×2`, TP на каждый вход, один buy-limit снизу. Размер входа — % от **Grid-USDC**, не от всего депо (иначе Core «подкармливает» сетку и пропорция плывёт).

Учёт вести раздельно: `Core_BTC / Grid_BTC / USDC`, в Excel — отдельные колонки (сейчас всё смешано). Иначе паритет с холдом не посчитать.

## 4. Апгрейд сетки под тренд (частичный TP + runner)

Триггер тренд-режима — первичный: закрытие выше `MA(N)` (N с калибровки, старт MA 50×4h); условие `current > max_TP` (новые хаи) — только подтверждающее. Причина: пирамидинг срабатывает раньше (`max_TP − STEP×AGGR`), уводя `max_TP` вверх, поэтому `current > max_TP` в одиночку в монотонном росте почти не наступает. Выход из тренда — закрытие ниже `MA(N)` минус полоса гистерезиса. `min_TP/max_TP` считаются только по висящим sell (`modules/delayed_orders_strategy.py:1497–1502`); runner без висящего sell в расчёт не входит и ведётся отдельно.

- **Range-режим (боковик):** как сейчас — целый TP `entry + STEP`, обычный пирамидинг `AGGR=0.5`.
- **Trend-режим (рост):**
  - **Частичный TP:** продаём 50% входа на `entry + STEP`, остаток (runner) — со стопом `max(цена входа + запас комиссий, достигнутый максимум − STEP×TRAIL_STEP_MULT)` (старт `TRAIL_STEP_MULT=2`). Runner даёт захват тренда.
  - **Пирамидинг агрессивнее:** `AGGR 0.5 → 0.2–0.3` (докупаем ближе к хаям) + размер входа Grid ×1.25–1.5 в тренде (кап — чтобы не съесть Grid-USDC за 3 входа).
  - **TP шире:** вторая половина идёт не за $600, а за трейлингом — в сильном тренде это кратно больше STEP.
- **На развороте вниз:** runner закрывается по трейлингу, режим возвращается в Range, усреднение вниз — только на Grid-деньги.

Изменения в коде (для build-режима):

1. `settings.py`: `STEP_PCT` (вместо/рядом с `STEP`), `CORE_PCT=50`, `TREND_MA_N`, `PARTIAL_TP=0.5`, `TRAIL_STEP_MULT=2`, `PYRAMID_AGR_TREND`, `GRID_RISK_PCT`.
2. `delayed_orders_strategy.py`: разделение балансов Core/Grid; блок детектора режима; ветвление TP (целый vs частичный+runner); трейлинг-стоп для runner; раздельный Excel/TG-учёт. Матчинг buy/sell усложнится: один buy → два sell (TP1 + runner) — `find_matching_buy_trade` расширить (поле `leg: tp1/runner`).
3. Метрика паритета: на каждой итерации считать `hold_benchmark = депо_старт / цена_старт × цена_сейчас` и писать рядом с `Total Value`. Цель релиза: в бэктесте на растущем отрезке `Total ≥ 0.8–0.9 × hold`, в боковике `Total > hold`.

## 5. DoD и порядок

1. Калибровка BTC: ATR, STEP% (старт 0.5%), `MA(N)` — цифры из истории свечей (источник см. §2), не с потолка; плюс количественная проверка funding-гипотезы из шапки (история ставок funding по BTC — вне репозитория).
2. Папер/бэктест на двух отрезках истории: боковик и рост. Критерий — метрика из §4.
3. Живой прогон малыми суммами: Core покупается, Grid крутит, runner отрабатывает первый тренд без ручного вмешательства. Критерий прохождения: ≥20 закрытых Grid-циклов без ошибок матчинга buy/sell, средний STEP-профит в пределах ±15% от бэктеста, ≥1 закрытие runner по трейлингу.
4. Доки (в репозитории отсутствуют — создать): `PLAN.md` (новый этап «Spot BTC Core+Grid»), `base-context.md` (пометка о заморозке перпов и статусе funding-гипотезы), CHANGELOG (bump `settings.version` следующим релизом).

Риски: Core на −30% медвежки тащит equity вниз (плата за паритет с холдом); runner усложняет матчинг и статистику; первый подбор `MA(N)`/`TRAIL` может пилить. Лечится капами и бэктестом, архитектура не меняется.
