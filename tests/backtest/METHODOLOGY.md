# Методика исследования GridRB на новой монете

Назначение: чтобы другой агент (или человек) мог **повторить** исследование
GridRB на любой монете и получить сопоставимые результаты. Описывает порядок
шагов, команды, критерии отбора и подводные камни. Отчёты-примеры:
`REPORT_gridrb_3y.md` (BTC), `REPORT_sol_3y.md` (SOL).

## 0. Главный принцип: гонять боевой движок, а не копию

В `tests/backtest/strategies.py` лежит **порт** логики GridRB. Он успел
разойтись с боевым кодом (нет гистерезиса перестановки, ранней докупки и т.п.):
на одних и тех же BTC H1 порт давал −24.6 п.п. к hold, а боевой движок −17.6.

Поэтому все новые исследования — только через
`tests/backtest/minute_replay.py`, который вызывает
`modules/gridrb_strategy.GridRBEngine` (тот же класс, что в бою) и
`GridRBConfig.from_settings()`. `strategies.py` использовать нельзя, кроме
исторических отчётов.

## 1. Данные

Источник — официальный дата-API Binance `https://data-api.binance.vision`
(публичный, без ключей). Окно по умолчанию: **2023-11-01 → 2026-11-01**
(3 года), интервал `1h`, файл `data/<coin>_h1_3y.csv`.

Если монеты ещё нет в списке:

```bash
# добавить тикер (например, "APT") в COINS в fetch_data_multi.py, затем:
./venv/bin/python tests/backtest/fetch_data_multi.py
```

Проверка файла (число строк должно быть ≈ 26 305, границы — 2023-11-01 и
2026-11-01):

```bash
head -2 tests/backtest/data/<coin>_h1_3y.csv
tail -1 tests/backtest/data/<coin>_h1_3y.csv
wc -l   tests/backtest/data/<coin>_h1_3y.csv
```

**Точность размера (`sz_decimals`) важна.** Она своя у каждого токена
Hyperliquid; в бэктесте от неё зависит округление количества. Узнать:

```bash
curl -sS -X POST https://api.hyperliquid.xyz/info \
  -H 'Content-Type: application/json' -d '{"type":"spotMeta"}' \
  | ./venv/bin/python -c "import json,sys; m=json.load(sys.stdin); \
    print({t['name']: t['szDecimals'] for t in m['tokens'] if t['name'] in ('UBTC','UETH','USOL','UAVAX','HYPE')})"
```

На момент написания: `UBTC=5, UETH=4, USOL=3, UAVAX=3, HYPE=2`.
В `optimize_live.py` и `minute_replay.py` передаётся флагом `--sz-decimals`.

Оговорка: это цены Binance в USDT, а не спот Hyperliquid (UBTC/USDC и т.д.).
Уровни и микроструктура немного другие; для сравнения стратегий между собой и
с hold этого достаточно.

## 2. Базовая конфигурация (текущая боевая)

```bash
./venv/bin/python tests/backtest/minute_replay.py \
  tests/backtest/data/<coin>_h1_3y.csv --sz-decimals <N>
```

Печатает финал, доходность, maxDD, сравнение с hold, число сделок по типам.
Так фиксируется «точка отсчёта» до любых изменений параметров.

## 3. Перебор параметров

```bash
# обычная модель исполнения («касание уровня = исполнено»)
./venv/bin/python tests/backtest/optimize_live.py --coin <COIN> \
  --n 600 --workers 3 --rounds 3 --seeds 3

# консервативная модель (цена должна «проткнуть» уровень на 0.05 %)
./venv/bin/python tests/backtest/optimize_live.py --coin <COIN> \
  --n 600 --workers 3 --rounds 3 --seeds 3 --penetration 0.0005
```

Что делает скрипт:
- окно **70/30**: первые 70 % баров — обучение, последние 30 % — проверка
  (out-of-sample, старт заново с $10 000);
- 600 случайных конфигураций (seed 42) из сетки
  `f0 × band × delta × n × micro_lot × micro_max × early_lot × rearm_eps`
  + боевая конфигурация и варианты из спеки;
- покоординатное уточнение лучших (`--rounds`, `--seeds`);
- критерий отбора: максимум `excess` к hold при
  `maxDD ≤ 1.2 · maxDD_hold`; дополнительно считается Calmar;
- пишет `results/optimize_<coin>_train.csv` (все кандидаты, обучение) и
  `results/optimize_<coin>_best.csv` (финалисты: train / test / full).

## 4. Проверка на режимах (скользящие окна)

```bash
./venv/bin/python tests/backtest/sol_rolling.py --coin <COIN> --workers 3
```

- 180-дневные окна (4 320 H1-баров), шаг 14 дней → ~66 независимых стартов;
- режим окна по доходности hold: падение < −10 %, флэт −10…+10 %, рост > +10 %;
- метрики по конфигурациям: средний/медианный excess, win-rate, средний DD,
  excess отдельно в падении/флэте/росте;
- **walk-forward**: первые 60 % окон — «выбор», последние 40 % — «проверка»;
  печатается корреляция среднего excess между ними.

Набор конфигураций задаётся в `CONFIGS` в начале файла — при исследовании
новой монеты туда стоит положить боевую конфигурацию, финалистов перебора и
несколько «крайних» вариантов (низкий/высокий `f0`, широкий/узкий `delta`).

Пишет `results/<coin>_rolling_windows.csv` и
`results/<coin>_rolling_summary.csv`.

## 5. Как читать результаты (правила, а не цифры)

1. **Train → test.** Смотрите не на «лучший на обучении», а на `test_excess`.
   Если на обучении +40…+60 п.п., а на проверке +5…+10 п.п. — это
   переобучение, а не находка.
2. **Модель исполнения.** Прогоните перебор в двух режимах
   (`--penetration 0` и `0.0005`). Если победители разные, а итог сильно
   гуляет — выбор параметров по истории ненадёжен. Бэктест **не** моделирует
   очередь мейкера, поэтому цифры — верхняя оптимистичная граница.
3. **Walk-forward корреляция.** Если корреляция «выбор vs проверка»
   отрицательная (на BTC −0.977, на SOL −0.860), ранжирование параметров
   переворачивается при смене режима: переносить оптимум с одного отрезка на
   другой нельзя.
4. **Полное окно ≠ среднее по окнам.** Один скомпаундированный путь и
   равновесная выборка окон могут расходиться (на SOL: +8.3 п.п. против
   −1.5 п.п.). Для «среднего случая» честнее окна.
5. **Что вообще означает excess.** Стратегия держит ~`f0` монеты, поэтому в
   устойчивом росте она структурно отстаёт от hold, а в падении/флэте —
   выигрывает. «Обогнать hold на всём бычьем пути» — не цель и не критерий.

## 6. Отчёт

Создайте `tests/backtest/REPORT_<coin>_3y.md` по образцу `REPORT_sol_3y.md`:
данные и окно, базовая конфигурация (таблица против BTC), перебор в двух
моделях исполнения, скользящие окна с walk-forward, итог, ограничения, файлы.
Все числа должны быть воспроизводимы командами из §1–4.

## 7. Подводные камни (проверено на практике)

- **Python 3.14 и пул процессов.** Стартовый метод по умолчанию —
  `forkserver`, поэтому воркеры **не наследуют** глобальные переменные,
  заданные после импорта. Любые параметры (sz_decimals, penetration) нужно
  передавать через `initargs` инициализатора, а не через модульные глобалы.
  Иначе поиск молча посчитает не то (эта ошибка была и исправлена).
- **`sz_decimals` по умолчанию 5** — верно для BTC, но не для SOL (3). Для
  новой монеты всегда проверяйте `spotMeta`.
- **`data/` в `.gitignore`** — сами CSV в репозиторий не попадают, но скрипты
  скачивания воспроизводят их из первоисточника.
- **Окна перекрываются** (шаг 14 дней при длине 180) — это не независимые
  наблюдения, статистическую значимость по ним считать нельзя.
- **Один исторический путь** — любые выводы условны; «оптимум» может быть
  ставкой на режим.
- **Не менять боевой код** (`main.py`, `modules/`) в рамках исследования.
  Если найден кандидат на изменение — это отдельное решение владельца.
